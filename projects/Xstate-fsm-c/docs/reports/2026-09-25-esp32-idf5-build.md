# Original ESP32 IDF5 Build Report

## Scope

This report records clean, like-for-like disabled and XFSM-enabled builds for
the original ESP32 using Espruino's `ESP32_IDF5` board definition. It verifies
32-bit Xtensa compilation, linking, optional-library integration, and app-image
partition headroom. It does not claim physical-device runtime or conformance.

## Revisions And Environment

- XState-Espruino-Project evidence base: `2c0d26f`
- Profile 1 specification: `0.49`
- Espruino implementation: `de251bd977cc5b6bdccd83f72b872a0911fd6866`
- Official Espruino base: `84c190da7feb10a976d7ca422be39adaa10fb3c2`
- Conformance cases: `XFC-CF-RESOURCE-001`, `XFC-CF-BUILD-004`
- Board: `ESP32_IDF5`
- CPU: original ESP32, 32-bit little-endian Xtensa LX6
- SDK: ESP-IDF 5.5.3
- Compiler: `xtensa-esp-elf-gcc` 14.2.0
- Result: [machine-readable build record](../../tests/results/esp32-xtensa/2026-09-25-m5-idf5-build.json)

The target environment was installed and selected with
`source scripts/provision.sh ESP32_IDF5`. The inherited Codex-shell
`DEBUG=release` variable was removed so the build used the release flags rather
than enabling Espruino's debug Make branch. The normal board configuration
still applies `-Og` to Espruino component sources, while ESP-IDF itself is
configured for size optimization; both comparison builds used these same
settings.

## Procedure

```bash
env -u DEBUG make BOARD=ESP32_IDF5 RELEASE=1 USE_XFSM=0 clean
env -u DEBUG make BOARD=ESP32_IDF5 RELEASE=1 USE_XFSM=0 -j2
env -u DEBUG make BOARD=ESP32_IDF5 RELEASE=1 USE_XFSM=1 clean
env -u DEBUG make BOARD=ESP32_IDF5 RELEASE=1 USE_XFSM=1 -j2
```

The enabled generated configuration contained `USE_XFSM`, included
`libs/xfsm/`, and compiled `libs/xfsm/jswrap_xfsm.c` as an ESP-IDF main
component source.

## Measurements

| Measurement | Disabled | XFSM enabled | Delta |
| --- | ---: | ---: | ---: |
| App image | 1,491,968 | 1,519,872 | 27,904 |
| ELF `text` | 1,312,223 | 1,337,403 | 25,180 |
| ELF `data` | 202,860 | 205,596 | 2,736 |
| ELF `bss` | 40,849 | 40,849 | 0 |

The app image increased by 1.87%. The enabled image occupies 74.21% of the
2,048,000-byte app partition and leaves 528,128 bytes free. Both builds passed
ESP-IDF's partition-size check.

## Decision And Limits

Original ESP32 with ESP-IDF 5 is suitable as the primary high-resource and
Xtensa physical-development target and advances to `Build verified`. This
result does not freeze the native layout or close M5: physical RAM, timing,
stack, GC, and completion-chain evidence are still required. The stock
`ESP32_IDF5.py` board definition was not changed; final product packaging must
select `XFSM` through a dedicated board configuration or equivalent normal
Espruino build selection.
